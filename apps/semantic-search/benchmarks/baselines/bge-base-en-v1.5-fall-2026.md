# BGE baseline: Fall 2026

Recorded locally on October 20, 2026 PDT using the existing
`BAAI/bge-base-en-v1.5` implementation, an isolated Redis Stack instance with
the production 140 MB limit and `volatile-lru` policy, and the current
semantic-search container image.

The full generated catalog snapshot and raw reports were written to temporary
local storage rather than committed because the snapshot is 2.6 MB and can be
regenerated by `capture_catalog.py`.

## Relevance

| Metric | BGE result |
| --- | ---: |
| Recall@10 | 0.785714 |
| MRR@10 | 0.661565 |
| nDCG@10 | 0.671603 |

The strongest category was short topic search. The starter set exposed three
useful weaknesses to compare against MiniLM: `CS 61A` did not return COMPSCI
61A in the top ten, the natural-language DATA C8 query missed DATA C8, and the
natural-language BIOLOGY 1A query missed BIOLOGY 1A.

These query timings call the engine directly and exclude HTTP and internet
latency. The deployed endpoint run produced the same relevance metrics, which
confirms that the isolated baseline follows the production ranking path.

## Memory

| Measurement | BGE result |
| --- | ---: |
| Process RSS after model load | 445.7 MiB |
| Process RSS after index build | 2,453.8 MiB |
| Peak process RSS | 2,546.2 MiB |
| Redis before build | 1.35 MiB |
| Redis after build | 48.04 MiB |
| Redis increase for one term | 46.69 MiB |
| Redis vector index | 16.66 MiB |
| Redis inverted index | 3.88 MiB |

One BGE term consumes roughly one third of the entire 140 MB production Redis
budget. Retaining two similarly sized terms can approach 100 MB before normal
application cache data is counted. The full Redis increase is the safer budget
metric because `FT.INFO`'s reported total index memory does not include all
document/hash storage.

The query embedding cache contained 21 entries after the run, with 21 misses
and 42 hits. Its raw vector payload is small and bounded at 256 entries; the
dominant risks are build-time process memory and persistent Redis index data.
